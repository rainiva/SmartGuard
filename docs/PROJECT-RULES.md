# SmartGuard 完整项目规则

**适用范围：** SmartGuard 的需求分析、开发、修复、重构、测试、发布与文档维护。

**维护模型：** 个人维护为主；规则优先降低错误成本，不引入不必要的会议、审批、角色或台账。

**入口：** [AGENTS.md](../AGENTS.md)；具体架构真源：[ARCHITECTURE-CONTRACT.md](ARCHITECTURE-CONTRACT.md)。

## 1. 规则目标

项目最高级不变量是：

> 所有改动都应让系统在功能增加后仍保持入口清楚、真源唯一、责任明确、边界稳定、状态可解释、失败可恢复、修改可验证、性能可预测、资源有上限。

由此派生以下原则：

1. 一个事实只有一个真源。
2. 一个业务能力只有一个规范语义入口。
3. 一个责任只有一个明确拥有者。
4. 模块边界清楚，依赖方向单向。
5. 状态只能通过规定的转换或写入入口改变。
6. 副作用必须可定位、可控制、可恢复。
7. 数据、接口和可观察行为变化必须有迁移或明确破坏策略。
8. Bug 必须修根因并形成回归防线。
9. 测试必须覆盖受影响业务链；关键桌面流程必须有真实用户路径证据。
10. 临时方案、兼容层与旧架构必须有退出条件。
11. 高影响改动先做影响分析，再编码。
12. 复杂度只能有理由地增加，并应随迁移完成而下降。
13. 每个关键业务路径必须有明确的成本模型和资源上限。
14. 性能是系统契约的一部分，禁止用未经设计的低效实现换取功能完成。

系统不仅要在正常路径工作，还要在失败、过载、长期运行、休眠唤醒、版本升级和规模增长时保持可预测。局部故障默认只造成局部影响；持续性核心能力停止工作却无人知晓，比显式失败更危险。

这些原则是决策工具，不要求为每次小改填写表格。只有风险触发时才升级流程。

## 2. 风险分级与最小流程

### 2.1 低风险

适用：纯文档、注释、格式、明确的配置值、无行为变化的私有整理。

流程：读取目标 → 精确修改 → 文档/格式/编码检查 → 检查 diff → 提交。

不需要 RED，也不需要全量 `Run-Tests.ps1`；若无法证明无行为变化，升级为标准改动。

### 2.2 标准改动

适用：单一功能、Bug、局部 UI 行为、脚本行为、内部 API 或可测试逻辑变化。

流程：复现或行为测试 RED → 根因/边界确认 → 最小 GREEN → 相关回归 → 必要重构 → 全量门禁 → 用户路径验收（如适用）→ 提交。

### 2.3 高影响改动

满足任一项即视为高影响：

- 同时穿透三个及以上层级或多个进程；
- 修改公共契约、配置结构、持久化格式、状态机或生命周期；
- 修改安装、升级、卸载、计划任务、UAC、shell 集成；
- 修改共享基础设施或 `ARCHITECTURE-CONTRACT.md` 中登记的真源/入口；
- 引入/替换重要依赖，或需要兼容旧数据、旧行为、旧入口；
- 进入高频或大数据路径，新增轮询、队列、缓存、并发、批处理、全量扫描或大集合 UI 更新；
- 改变时间、顺序、一致性、取消、恢复、数据生命周期、部署或回滚语义；
- 改动范围无法在一个语义完整的小提交中安全说明。

实现前写一份简短变更说明并检查 §2.4 Change Impact Matrix，不强制工单。只展开受影响项，其余标记 `N/A`。说明至少回答：

- 现状、根因、目标行为和不可改变的外部契约是什么？
- 入口、真源、Owner、状态转换和副作用在哪里？
- 旧入口、旧数据、临时兼容与失败中间态如何迁移、恢复、删除或回滚？
- 用什么自动化、真实用户路径和运行证据证明完成？

信息不全时先调查；不得靠边写边猜扩大 diff。

### 2.4 Change Impact Matrix

仅标准改动中确有相关风险或高影响改动需要检查；低风险改动不填表。

| 影响域 | 核心问题 |
|--------|----------|
| Function | 用户行为、输入输出、错误语义或副作用是否改变？ |
| Architecture | 边界、依赖、入口、真源、Owner、认知负担或变化传播范围是否改变？ |
| Data | Schema、配置、状态、陈旧度、保留、归档、删除、重建或迁移是否改变？ |
| Performance | 频率、规模、复杂度、IO、延迟、吞吐或 UI 工作量是否改变？ |
| Resource | 内存、线程、Task、队列、缓存、句柄、Timer、订阅或临时文件是否有界？ |
| Concurrency & Time | 锁、竞态、顺序、重复、取消、所有权转移、时钟或休眠唤醒语义是否改变？ |
| Reliability | 新增哪些失败、过载、部分成功、依赖不可用或静默停工模式？ |
| Recovery | 崩溃、中断、重复执行或迁移失败后如何恢复到确定状态？ |
| Compatibility | 旧数据、旧配置、旧 API、旧脚本或跨版本组合是否仍可工作？ |
| Security | 权限、提升、信任边界、敏感数据、日志与诊断导出是否改变？ |
| Observability | 问题能否被发现、关联、定位，并区分正常降级与真实故障？ |
| Operations | 构建、安装、升级、卸载、回滚、备份与现场恢复是否改变？ |

矩阵是防漏清单，不是文档负担。没有证据证明受影响的域不得凭想象扩张范围；确认受影响的域必须进入设计、测试和完成定义。

### 2.5 关键模块治理

Change Impact Matrix 检查“改动影响哪些质量属性”；关键模块治理检查“改动落在哪个一旦设计错误就会污染全局的基础能力”。两者按实际影响组合使用，不为普通业务改动增加第二套流程。

SmartGuard 当前只登记真实存在且需要额外保护的模块：

| 等级 | 关键模块 | 必须保持的模块不变量 |
|------|----------|----------------------|
| L0 系统生存级 | 配置 | `GuardConfigRepository` 与已登记 mutation API 是唯一读写入口；同一配置项只有一个可解释的最终值；跨线程/进程写入不得丢更新；替换失败时旧配置仍可恢复。 |
| L0 系统生存级 | 日志 | 普通日志失败不得拖垮守护主链；队列、批量、磁盘和保留期必须有界；敏感信息不得进入普通日志；关闭或降级失败必须可观察。 |
| L0 系统生存级 | 运行状态与文件持久化 | 状态有明确单写者；临时文件完成后才能原子替换正式文件；崩溃或中断不得把最后一个有效版本先删除；派生状态和缓存可重建。 |
| L0 系统生存级 | 后台任务、进程与计划任务 | 每项长期工作都有 Owner、唯一身份、启动、取消、超时、并发上限和退出语义；重复启动不得产生多份核心任务；外部进程退出码和失败不得静默丢失。 |
| L0 系统生存级 | 时间 | 持久化期限使用明确的 UTC 语义，显示时再做本地转换；进程内持续时间和冷却优先使用单调时钟；核心逻辑不得依赖不可注入的散落 `DateTime.Now`。 |
| L1 信任与数据级 | 更新、安装、迁移与 UAC | 流程至少区分 Check、Download、Verify、Prepare、Install、Validate、Commit；提权前验证包的来源与完整性；部分成功、中断、重复执行和回滚后状态必须确定。 |
| L1 信任与数据级 | Secret 与诊断数据 | Secret 不进入源码、普通配置、日志或测试夹具；诊断导出按既有 Redactor 脱敏并限制范围。项目没有 Secret 时，不预建 SecretStore。 |
| L2 协调级 | 网络调用与通知 | 远程调用必须显式定义超时、取消、大小/并发边界和可重试错误；通知具有去重、冷却或速率边界，失败不得改变核心策略状态。 |

改动命中上述模块时，在现有变更说明中增加一个很短的 **Critical Module Check**：

1. 写明命中的模块、当前 Owner、真源和规范入口。
2. 列出本次必须保持的 2–5 个模块不变量；稳定且会跨任务复用的不变量才分配 `CFG-INV-*`、`LOG-INV-*` 等标识并登记到 `ARCHITECTURE-CONTRACT.md`。
3. 将模块不变量与 §2.4 中真实受影响的域组合，形成测试；不为无关维度凑用例。
4. 至少覆盖正常路径、一个主要失败路径，以及本次实际涉及的重复、并发、中断或恢复场景。
5. 修改 Owner、入口、持久化格式或稳定不变量时，同步架构契约和架构门禁。

只有满足以下任一条件，才为某个模块拆独立规则文件：规则已无法在本节清楚表达；同一模块连续多次变更并反复遗漏同类风险；或已经形成独立的架构/测试门禁。否则继续维护本节，禁止先为鉴权、支付、消息总线、缓存、搜索、同步、插件等当前不存在的能力预建规则包、框架或台账。

## 3. 任务开始与范围控制

每次任务开始时：

1. 确认当前目录是目标 Git 仓库，查看实时 `git status --short`。
2. 保护用户已有修改与未跟踪文件；只操作任务范围内文件。
3. 写入前读取目标文件；新文件必须先确认不存在。
4. 阅读 `AGENTS.md`、本规则相关章节和架构契约相关条目。
5. `.codegraph/` 存在时，理解代码优先使用 CodeGraph；随后只做必要的窄搜索和读取。
6. 明确需求、范围外事项、验收口径和所需验证层。
7. 涉及平台语义时查询当前官方文档，记录关键行为依据。

禁止“顺便优化”。范围外发现只记录，除非它直接阻塞当前任务或证明当前方案错误。

## 4. 文件、编码与工作区安全

- C#、XAML、Markdown、JSON、XML、PowerShell、Inno Setup 等含中文文件统一使用 UTF-8 无 BOM。
- 读取和写入必须显式指定编码；手工修改使用 `apply_patch` 等精确补丁。
- 禁止 shell 整文件读改写、重定向回写、依赖控制台编码、复制终端非 ASCII 文本作为源内容。
- 终端显示异常不等于文件损坏；先做字节级或显式 UTF-8/UTF-16 验证。
- 删除、移动、清理前确认绝对目标与 Git 状态。不得清理用户文件或无关产物。
- 本地产物只使用 `Clean-Workspace.cmd -DryRun -AllLocal` 预览，再按需执行受控清理。

## 5. TDD 与 Bug 修复

### 5.1 RED → GREEN → REFACTOR

所有功能、Bug、行为与契约变化必须：

1. 先写或调整一个面向行为的测试。
2. 运行并确认它因目标缺口按预期失败，而不是因环境、编译或测试错误失败。
3. 保存 RED 命令、失败摘要和关键断言。
4. 只实现使当前 RED 通过的最小改动。
5. 跑相关测试转绿后，才允许整理结构。
6. 重构期间保持测试全绿，不改变未授权行为。

若已经先写生产实现，撤销本次实现，从 RED 重来。不得通过删除断言、Skip、放宽门槛或改测试迁就实现；只有需求或契约确实变化且有证据时才能改变测试标准。

### 5.2 Bug 根因门禁

无法复现时，可以继续调查，但不得声称已修复。修复前至少回答：

- 错误如何从真实入口发生？
- 根因位于哪个责任 Owner？
- 哪个不变量或契约被破坏？
- 为什么现有测试没有发现？
- 是否存在同一模式的其他实例？

修复应落在拥有责任的最低正确层。若删除 UI 后问题仍存在，就不应由 UI 修正。发现事件未释放、配置旁路、状态绕写等模式时，应横向扫描同类位置，但只修与当前根因同属一个明确范围的实例。

## 6. 架构与复杂度治理

### 6.1 真源、入口与 Ownership

- 具体权威实现以 `ARCHITECTURE-CONTRACT.md` 注册表为准；扩展现有实现，不建立平行系统。
- 数据可以复制用于投影或缓存，但写入所有权不能复制；派生状态优先计算，不额外存储。
- 多个外部入口可以存在，但必须汇聚到同一语义入口；UI、CLI、计划任务和安装器不得各自实现业务规则。
- 模块必须能用一句话说明唯一职责。无法说明时，先重新划分边界，不把代码塞进 `Common`、`Utils` 或万能 Manager/Service。
- 默认使用 `private`/`internal`；只有稳定的跨模块契约才公开。
- 认知复杂度也是技术债：维护者应能快速回答“从哪里进、谁负责、状态在哪、失败去哪查”。小范围状态变化不得无理由触发大范围重算、通知或 UI 刷新。

### 6.2 依赖方向

推荐方向：Presentation → Application/Configuration orchestration → Domain/Contracts；Infrastructure 实现核心层定义或消费的明确契约。

- UI 不直接决定领域规则、解析配置文件、修改运行状态或调用底层持久化细节。
- 核心规则不依赖 WPF、具体数据库、Windows UI 或安装器。
- Windows API、文件、注册表、进程、计划任务和第三方 SDK 应收口到现有基础设施边界。
- 不允许项目、模块或领域循环依赖；不得为少改文件而反转依赖。

### 6.3 状态、并发与生命周期

- 区分领域状态、运行状态、持久化状态、外部系统状态、UI 状态和派生状态。
- 共享可变状态必须有明确单写者或同步策略；禁止多个线程任意写入。
- 长期 Task、Timer、Watcher、Process 和事件订阅必须明确创建者、Owner、启动、取消、停止、等待退出、异常处理和释放。
- 谨慎使用 fire-and-forget；异常必须可观察，退出时任务必须可收敛。
- 事件默认用于通知、投影、遥测或非关键副作用，不得悄悄成为第二条核心业务链。
- 时间敏感逻辑必须区分 UTC、本地 wall clock 与单调耗时；设计要覆盖系统时间调整、时区、跨日、睡眠唤醒和 Timer 漂移。不得让散落的 `DateTime.Now` 决定不可测试的核心行为。
- 并发或消息流程必须明确顺序要求、重复处理和一致性模型；禁止依赖“碰巧先发生”。需要时明确 at-most-once、at-least-once 或幂等语义，不轻率承诺 exactly-once。
- 取消是正式协议：说明取消是请求还是保证、已经发生的副作用、何时真正结束、是否补偿，以及调用者何时可以释放资源。
- 资源或任务交给队列、Scheduler、Writer 或后台服务时，必须明确所有权何时转移，以及新的取消、等待、Dispose 和失败处理 Owner。
- 对调度、同步和难复现并发问题，优先注入 Clock、输入、Seed 或事件序列，使关键场景可确定复现和重放；不为普通确定性逻辑额外建设框架。

### 6.4 错误、副作用与恢复

设计同时覆盖成功、失败、超时、取消、重复执行、并发执行、部分成功、进程退出和依赖不可用。

- 所有文件、注册表、进程、任务、网络、日志与 UI 调度副作用都应可定位。
- 多步骤操作要定义成功点、幂等性、可重试条件、回滚或补偿策略。
- 禁止空 `catch`。捕获异常必须用于恢复、转换、补充上下文、受控重试、降级或终止。
- Retry 必须限定异常、次数、退避和幂等条件；禁止无限或盲目重试。
- 日志不得成为一般业务成功的前提；日志故障应隔离并按现有降级链处理。
- 中断、崩溃或部分成功后必须能恢复到一个可解释的确定状态；恢复操作尽量幂等，并区分继续、回滚、重建和人工介入。
- 局部故障默认限制在所属 Failure Domain；日志、通知、插件或非核心投影失败不得拖垮核心守护链。
- 过载行为是产品契约。提前选择限流、背压、拒绝、丢弃低优先级、批处理或只保留核心功能，禁止无限接收后等待 OOM。
- 持续性核心能力（Watcher、后台循环、同步、持久化）停止时必须产生可观测的健康信号或显式失败；禁止“进程仍在但核心能力已静默死亡”。

### 6.5 临时结构与删除

临时代码、Feature Flag、Adapter、兼容层和旧入口一旦引入，必须记录用途、退出条件和删除阶段。高影响迁移应按“新入口建立 → 调用迁移 → 旧入口无调用 → 旧实现/配置/测试/文档删除”的方向单调收敛。

完成标准是目标架构成立，而不是旧架构与新架构永久并存。重复两次不自动抽象；只有同一稳定概念反复出现且边界明确时才提取公共抽象。

## 7. 配置、数据、接口与兼容

- 配置只能经 `GuardConfigRepository` 和已登记 mutation API 访问；新增字段必须登记读取、默认、迁移、写入 Owner 和兼容行为。
- 持久化格式和 Schema 视为正式契约。修改前定义备份、迁移、重复执行、失败恢复和旧版本兼容。
- 持久化数据、日志、缓存、索引、临时文件和历史记录必须明确创建、使用、更新、归档、保留、删除与重建策略；不得只设计“写进去”。
- 缓存、UI Projection、索引与跨进程状态必须定义允许陈旧度和刷新触发条件。Freshness 是契约，既不默认绝对实时，也不允许偷偷展示无限期旧数据。
- 外部可观察行为不得静默改变。参数、返回、错误语义、持久化结果、用户可见状态或副作用变化必须进入需求、变更记录或 ADR。
- 兼容性必须逐项决定 `Keep / Migrate / Deprecate / Break / Delete`，不能默认永久保留。
- 模块边界输入一律验证格式、范围、语义、权限和当前状态。

## 8. 测试与验收

测试跟随影响面与业务链，不跟随文件数量。

### 8.1 分层

- 单元测试：纯逻辑、解析、格式化、不变量与边界条件。
- 集成测试：配置、文件、进程、计划任务、安装/卸载和跨组件协作。
- 架构测试：禁止第二真源、第二入口、越层依赖、退役路径和硬编码回流。
- 真实桌面验收：从真实窗口、托盘、安装器或用户命令入口执行完整路径。

测试应断言输入、输出、状态变化、副作用和不变量，避免依赖 private method、内部类或无关调用顺序。重构还应做不存在性验证：旧入口、旧字面量、旧配置和旧调用已经不可达或已删除。

### 8.2 运行门禁

先运行最窄的 RED/GREEN 测试；行为改动完成前运行：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Run-Tests.ps1
```

验证必须以进程退出码和 `.work/test-results/` 的 summary JSON 为准，不能只看 stdout 或局部计数。回复中逐层报告：

- Pester；
- .NET 项目测试与架构测试；
- Tray Integration；
- Installer Integration；
- 每层 Passed / Failed / Skipped / Total、退出码及跳过或阻塞原因。

Tray/Installer 集成可能需要 UAC。用户取消、环境不支持、测试被 tier 或环境变量跳过时，记录为 `BLOCKED`、`NOT RUN` 或 `SKIPPED`，不得折算为通过。

### 8.3 UI 验收

UI 自动化通过仍不等于真实窗口体验通过。根据影响面检查：

- 从真实用户入口可到达并完成操作；
- 数据绑定、Dispatcher、异步刷新与退出生命周期；
- 键盘、焦点、Automation Name/HelpText 和状态播报；
- 100%/200% DPI、高对比度、减少动画中的相关路径；
- 滚动、拖动、长列表、窗口缩放等需要手感的行为。

未实际执行的人工听觉、视觉或长时间观察项必须如实列出。

## 9. UI 设计规则

SmartGuard 是 Windows 桌面工具，不采用通用 Web Dashboard 风格。

- 遵循当前 Fluent 桌面交互与密度习惯，界面轻量、平静、直接。
- 优先通过字号、间距、对齐、分组和留白建立层级；减少边框、卡片套卡片、重复标题与说明。
- 一个页面只突出主要任务；次要操作放入上下文明确的菜单或次级区域。
- 文案短而具体，危险操作表达后果并提供可恢复路径。
- 页面开始显得沉重时，先重审页面结构，不继续局部加容器和分隔线。

## 10. 日志、性能与安全

### 10.1 可诊断性

关键流程应能回答：谁从哪个入口触发、执行了什么、当前状态、外部依赖、结果、失败点和耗时。复用现有结构化事件、关联上下文、日志管线与诊断包，不建立第二套日志或导出链。

日志必须有容量边界、背压、降级、轮转与保留策略；敏感字段在诊断导出和日志中必须脱敏。

### 10.2 性能

功能正确和测试通过只是必要条件。可接受实现必须同时满足 Correctness、Architecture、Performance 与 Resource Safety。

#### 设计六问

关键业务逻辑、高频路径或大数据路径在实现前必须回答：

1. **Frequency：** 多久执行一次，由什么触发？
2. **Scale：** 典型、较大和极端情况下处理多少数据、文件或事件？
3. **Complexity：** 成本随规模如何增长，是否存在未经设计的 O(n²) 或更差路径？
4. **Resources：** 主要消耗 CPU、内存、磁盘、网络、线程、锁还是 UI 工作量？
5. **Bounds：** 队列、缓存、并发、批量、轮询和驻留数据的上限是什么？
6. **Incrementality：** 能否只处理变化部分，而不是重新扫描、计算或渲染全部内容？

低频、数据量固定的冷路径可以简要说明；不得为一次性或罕见路径做高复杂度微优化。

#### 性能红线

出现以下模式时默认触发性能审查，证明责任在实现者：

- 循环中执行数据库、磁盘、网络、序列化、反射或另一次大集合扫描；
- 可索引、批处理或增量完成，却采用全表扫描、逐条 IO 或全量重算；
- 高频 Timer 扫描全部状态，且无法说明为何不能事件驱动；
- UI 状态只变化一项，却重建完整集合、重新绑定或创建海量控件；
- 搜索、筛选等每次击键都启动昂贵且不可取消的工作；
- 创建无界 Task、线程、队列、缓存，或并发数量取决于输入规模；
- UI 线程执行文件 IO、大 JSON 解析、大集合排序、日志扫描或阻塞等待；
- 用 `Task.Run`、缓存或并行化掩盖错误算法和重复工作量。

这些模式并非绝对禁止；若真实规模很小或平台约束使其必要，必须给出规模、上限和测量证据。

#### SmartGuard 约束

- 日志、状态刷新和列表更新优先使用增量读取、分页、虚拟化、取消和局部 UI 更新；变化多少，更新范围原则上接近多少。
- 高频输入驱动的昂贵工作必须可合并、Debounce、取消或转入既有后台查询链。
- 轮询必须说明必要性、周期、单次成本、休眠/隐藏行为和降频策略；可明确感知状态变化时优先事件驱动。
- 队列、缓存和并发默认有界，并定义容量、背压、丢弃/淘汰、优先级和关闭策略。
- 高频小 IO 优先评估批处理，同时具有 `MaxBatchSize` 与 `MaxBatchDelay`，避免用吞吐换取无界延迟。
- Async 只改善阻塞体验，不自动降低总工作量；并行化必须基于工作负载和 Profiling，避免线程池饥饿、锁争用和内存压力。
- 启动路径只做首个核心操作所需工作，其他初始化按实际使用概率选择延迟、预热或后台执行。

现有预算和测试是当前真源：Engine 启动与内存使用由 `EnginePerformanceTests` 约束；日志工作台的大规模分页、P50/P95/Max 与工作集变化由 `LogWorkbenchPerformanceTests` 约束；日志页面导航响应由 `SettingsLogNavResponsivenessTests` 约束。修改相关路径时扩展这些测试，不新建平行性能口径。具体数值以测试和 `ARCHITECTURE-CONTRACT.md` 当前登记为准，规则文件不复制易漂移数字。

#### 测量与回归

- 设计阶段主动排除明显的 N+1、非线性扫描、无界资源和全量刷新；“不要过早优化”不能成为忽略基本成本模型的理由。
- 对已运行系统的优化遵循 Measure → Profile → Locate → Optimize → Measure Again，优先减少工作量，再优化单次执行速度。
- 性能改动必须保存同一环境、同一数据集、同一测量方法下的 Before/After，并说明 Latency、Throughput、CPU、内存、IO 或分配之间的取舍。
- 测试数据应接近真实规模；可能出现非线性增长时至少比较多个数量级并观察曲线，而不是只测一个小样本。
- 长期运行的 Engine、Timer、Watcher、队列、缓存或日志改动，应按风险增加稳态/Soak 验证，观察内存、句柄、线程和积压是否持续增长。
- 已登记预算变差、用户操作明显变慢、内存或队列无理由增长都属于 Regression；必须像功能回归一样处理。
- 没有新鲜测量证据，不得声称“性能已优化”。收益不足以覆盖复杂度成本时，保留更简单实现。

### 10.3 安全与依赖

- Secret、Token、密码、私钥和敏感连接信息不得进入源码、日志、测试夹具或提交历史。
- 默认最小权限；仅需要管理员权限的操作进行局部 UAC 提升，不把整个应用永久提升。
- 引入第三方库前检查维护状态、许可证、安全、依赖树、体积、平台支持与替代成本。
- 依赖升级尽量单独进行、单独验证，不把框架、UI、日志和运行时批量混升。

## 11. 文档与 ADR

- README 只保留项目说明、快速开始、常用命令和文档导航，不作为架构细节垃圾场。
- 影响 API、架构、配置、数据、行为、部署或恢复路径时，文档与代码同一提交更新。
- 只有昂贵、长期、存在真实替代方案的决策才写 ADR，例如核心架构、重要依赖、数据模型或不可逆兼容策略。
- ADR 记录 Context、Decision、Alternatives、Consequences；旧 ADR 不删除，变更时由新 ADR supersede。
- 注释解释“为什么”和陷阱，不复述代码；不保留注释掉的旧实现。

## 12. 构建、发布、Git 与磁盘卫生

- 同一提交应可构建、可运行、可测试；固定 SDK、依赖与正式构建入口，不维护个人私有构建步骤。
- GitHub Release 面向用户的标题、正文、安装和环境说明必须为简体中文；草稿真源为 `.work/release-notes/v{version}.md`。
- 发布前验证 Release 构建、安装包、安装/升级/卸载、计划任务、真实启动和恢复路径；自动化层与 UAC/桌面层分别报告。
- 安装、升级、迁移和回滚视为正式业务流程：明确旧程序/新程序与旧数据/新数据的允许组合、中途退出后的恢复、重复执行、备份和失败停止线。
- 一个提交完成一个意图，不混入无关重构、依赖升级或用户文件。
- 提交前检查 diff、敏感信息、临时产物和验证结果；只暂存当前任务文件，使用 Conventional Commits。
- 一轮有意义且可独立验证的改动完成后自动提交；禁止自动 amend、rebase、squash 或其他历史改写。

## 13. 停止线与完成定义

### 13.1 停止线

出现以下情况，停止继续堆代码：

- 找不到真正的 Source of Truth 或责任 Owner；
- 发现多个未知入口或调用链无法解释；
- 新旧实现开始同时承担责任且无退出计划；
- 不知道失败、取消或部分成功后的状态；
- 无法解释关键路径成本如何随规模增长，或出现无界队列、缓存、并发、轮询与全量工作量；
- 时间、顺序、一致性、取消或所有权转移语义不清，或持续性核心能力可能静默停止；
- 测试不断需要修改才能迁就实现；
- 修复不断扩大范围或制造更多 Adapter/Manager；
- 代码依赖执行顺序碰巧正确；
- 无法保护用户当前工作区或无法安全回滚。

返回调查、影响分析或设计阶段，直到重新建立可解释边界。

### 13.2 完成定义

根据风险选择适用项；不适用项明确标记，不为凑表格制造工作：

- [ ] 需求与验收标准满足，范围外事项未混入。
- [ ] 根因、入口、真源、Owner、调用链和副作用可解释。
- [ ] Change Impact Matrix 的相关域已检查，不适用项有合理边界且未制造额外流程。
- [ ] 命中关键模块时，Owner、入口、模块不变量及对应失败/恢复证据已检查。
- [ ] 不变量与外部契约符合预期。
- [ ] RED、最小 GREEN 和相关回归证据完整。
- [ ] 旧入口、旧实现、临时兼容和重复真源已删除或有明确退出条件。
- [ ] 全量自动化门禁有新鲜退出码与分层结果。
- [ ] 真实 UI / Tray / Installer / UAC 路径按影响执行，未执行项如实记录。
- [ ] 日志、错误、恢复、性能与安全风险按影响验证。
- [ ] 关键路径成本模型、资源上限和增量策略可解释；性能改动有真实规模 Before/After 证据。
- [ ] 中断恢复、重复执行、过载降级、数据生命周期、时间/顺序、升级与回滚按影响验证。
- [ ] 文档、架构契约、ADR、Changelog 或 Release note 已同步。
- [ ] Git diff 仅含本任务文件，提交语义完整。
